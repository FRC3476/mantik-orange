### Overview

`RobotContainer` is the central hub of command-based programming. It creates subsystems, configures default commands, and binds controller inputs to commands.

<RulesBox title="RobotContainer Responsibilities" subtitle="This class:">

- **Creates Subsystems:** Instantiate all subsystem objects.
- **Sets Default Commands:** Define what happens when no command is running.
- **Binds Controls:** Connect buttons/triggers to commands.
- **Provides Auto Commands:** Return autonomous routines.

</RulesBox>

Everything here is configuration. No loop logic belongs in `RobotContainer` — behaviour lives in commands.

### Basic RobotContainer

```java
package frc.robot;

import edu.wpi.first.wpilibj2.command.button.CommandXboxController;
import frc.robot.subsystems.intake.Intake;

public class RobotContainer {
    Intake intake = new Intake();
    private final CommandXboxController controller = new CommandXboxController(0);

    public RobotContainer() {
        configureButtonBindings();
    }

    private void configureButtonBindings() {
        intake.setDefaultCommand(intake.setIntakeCommand(0));

        controller.a().whileTrue(intake.setIntakeCommand(0.6));
    }
}
```

Bindings call the subsystem's own [command factories](/frc/commands). `intake.setIntakeCommand(0.6)` already requires the intake, so there is nothing to declare and nothing to forget.

### Button Bindings

`CommandXboxController` — and `CommandPS4Controller` / `CommandPS5Controller` for other hardware — expose each button as a `Trigger`:

<ContentTable
  headers={["Trigger method", "Runs when"]}
  rows={[
    ["<code>whileTrue(cmd)</code>", "While held; cancelled on release"],
    ["<code>onTrue(cmd)</code>", "Once on press; runs to completion"],
    ["<code>onFalse(cmd)</code>", "Once on release"],
    ["<code>toggleOnTrue(cmd)</code>", "Press starts it, press again cancels"]
  ]}
/>

```java
// Run intake while A is held
controller.a().whileTrue(intake.setIntakeCommand(0.6));

// Eject while B is held
controller.b().whileTrue(intake.setIntakeCommand(-0.4));

// Toggle with X
controller.x().toggleOnTrue(intake.setIntakeCommand(0.6));

// D-pad
controller.povDown().whileTrue(intake.intakeDeployCommand());
controller.povUp().whileTrue(intake.intakeHomeCommand());
```

### Composing Triggers

Triggers combine with `and`, `or`, and `negate`, which is how one button becomes a modifier for another:

```java
// R2 intakes — but only when R1 and triangle are not held
controller.R2().and(controller.R1().negate()).and(controller.triangle().negate())
    .whileTrue(intake.deployAndIntakeCommand());
```

R2 alone intakes; R2 with R1 held does something else entirely. No `if` statement in any periodic method.

You can also bind several commands to one trigger, each requiring different subsystems. The heading factory returns `AimAtGoalCommand` so you can keep the instance and pass `aim::isAligned`. Translation suppliers are already **blue-frame m/s**, not raw joystick axes. There is no shooter argument — chassis heading does not require the shooter.

`SmartShootCommand` here is only the parallel-binding shape. It must not require the drivetrain. It does not implement the shot table's feed gates. The complete composition is in [Swerve Aim at Goal](/frc/swerve-aim-at-goal). Right bumper holds aim. Left bumper is heading seed. Right trigger is explicit feed.

```java
controller.leftBumper().onTrue(drivetrain.runOnce(m_fusion::seedFieldCentric));

AimAtGoalCommand aim =
    AimAtGoalCommand.aimAtTargetCommand(
        drivetrain,
        FieldConstants::getGoal,
        m_fusion::isPoseTrusted,
        () -> teleopTranslation().getX(),
        () -> teleopTranslation().getY());
controller.rightBumper().and(RobotModeTriggers.teleop()).whileTrue(aim)
    .whileTrue(new SmartShootCommand(
        () -> drivetrain.getStateCopy().Pose, shooter, transfer, conveyor, table));
```

On a PS controller the same hold is `R1()`.

A `Trigger` is not limited to buttons — any `BooleanSupplier` works, so sensor conditions bind the same way:

```java
new Trigger(intake::hasGamePiece).onTrue(leds.flashGreenCommand());
```

### Default Commands

Default commands run when no other command requires the subsystem. Set them with `subsystem.setDefaultCommand(command)`.

```java
// Stop when nothing else is running
intake.setDefaultCommand(intake.setIntakeCommand(0));
shooter.setDefaultCommand(shooter.setDutyCycleSetpointCommand(0));

// The drivetrain's "resting state" is driver control in teleop, Idle otherwise
drivetrain.setDefaultCommand(
    Commands.either(
        drivetrain.applyRequest(() ->
            drive.withVelocityX(-controller.getLeftY() * MaxSpeed)
                .withVelocityY(-controller.getLeftX() * MaxSpeed)
                .withRotationalRate(-controller.getRightX() * MaxAngularRate)),
        drivetrain.applyRequest(() -> idle),
        DriverStation::isTeleopEnabled));
```

<RulesBox title="Default commands are how mechanisms stop">

Release the trigger, the command is unscheduled, and the scheduler can start the default command. That default is not a substitute for stopping hardware in `end()`.

Without a default command, the last request can stay applied. Every mechanism that can be left running needs a default command **and** an `end()` that writes a safe output.

Note the joystick axes are passed as **suppliers** inside `applyRequest`, not values captured once at binding time. The negations are because joysticks report forward as negative. Gate that default command to teleop so a finished auto cannot fall through to live sticks.

</RulesBox>

### Constructing the drivetrain

The course drivetrain is Tuner X `CommandSwerveDrivetrain`. Construct it once:

```java
public final CommandSwerveDrivetrain drivetrain = TunerConstants.createDrivetrain();
```

Intake, shooter, and other mechanisms you write yourself are still constructed once, unconditionally. REAL/SIM/REPLAY `ModuleIO` construction belongs only in the later [IO layer](/frc/io-layer) lesson, which is an optional AdvantageKit architecture — it does not plug into this generated drivetrain.

### The Auto Chooser

```java
private final SendableChooser<Command> autoChooser = new SendableChooser<>();

public RobotContainer() {
    autoChooser.setDefaultOption("Do nothing", Commands.none());
    autoChooser.addOption("Score left", m_autos.followFirstPath("score-left"));
    SmartDashboard.putData("Auto Chooser", autoChooser);
    configureButtonBindings();
}

public Command getAutonomousCommand() {
    Command selected = autoChooser.getSelected();
    SmartDashboard.putString("Auto/Selected", selected == null ? "none" : selected.getName());
    return selected;
}
```

`SendableChooser` is enough. Log the selected option when autonomous starts if you need the name in a match log. See [BLine](/frc/bline) for `followFirstPath` / later-path reset rules.

`Robot.java` schedules that command in `autonomousInit` and cancels it in `teleopInit` and `disabledInit`. Do not call subsystem `periodic()` by hand.

Optional SysId belongs in a setup-only block that does not collide with heading seed or aim. See [Swerve Drive Example](/frc/swerve-drive-example).

<RulesBox title="Common mistakes">

- **Reading a joystick axis into a variable** instead of passing a supplier.
- **Runtime logic in `RobotContainer`.** It configures; it does not decide.
- **A missing default command,** so a mechanism never stops.
- **Composing the auto before registering BLine event triggers.** `FollowPath` looks up each `lib_key` when the path runs; register the actions first.
- **Two bindings whose commands require the same subsystem,** so pressing one silently cancels the other.

</RulesBox>
