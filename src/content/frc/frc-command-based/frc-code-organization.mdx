### Command-Based Structure

A command-based project separates three concerns:

**Subsystems:** Physical hardware (drivetrain, intake, shooter) and the methods that control it.

**Commands:** Actions and logic — what to do and when.

**RobotContainer:** Setup and wiring — subsystem construction, button bindings, the auto chooser.

[WPILib Guide](https://docs.wpilib.org/en/stable/docs/software/commandbased/structuring-command-based-project.html)

### Directory Layout

A Tuner X generated project starts with `generated/TunerConstants.java`, `subsystems/CommandSwerveDrivetrain.java`, and `Telemetry.java`. Keep `BLineAutos` and `VisionFusion` out of generated files.

The AdvantageKit `drive/` package tree (`Drive.java`, `ModuleIO*.java`, `GyroIOPigeon2.java`) is an **optional later layout**. It does not replace `CommandSwerveDrivetrain` in this course. See [Hardware Abstraction with IO Layers](/frc/io-layer).

```
src/main/java/frc/robot/
├── Main.java
├── Robot.java
├── RobotContainer.java
├── Telemetry.java             // registerTelemetry callback
├── Constants.java             // mechanism IDs and setpoints you write
├── generated/
│   └── TunerConstants.java    // Phoenix Tuner X — do not hand-edit
├── subsystems/
│   ├── CommandSwerveDrivetrain.java
│   ├── VisionFusion.java      // sole camera poller; addVisionMeasurement
│   ├── intake/Intake.java
│   └── shooter/Shooter.java
├── vision/                    // camera reader (PhotonVision or Limelight)
│   └── VisionSubsystem.java
├── autos/
│   └── BLineAutos.java        // FollowPath adapter — not a generated file
├── commands/                  // multi-subsystem commands only
│   ├── AimAtGoalCommand.java
│   └── SmartShootCommand.java
└── util/
    └── PhoenixUtil.java
```

<RulesBox title="Note what is not in commands/">

There is no `RunIntakeCommand` and no `SetShooterSpeedCommand`. Single-subsystem actions are **factory methods on the subsystem itself** — see [Commands](/frc/commands).

The `commands/` package holds only commands that coordinate several subsystems and cannot be written as a factory. Keeping it small is the point: everything the intake can do lives in `Intake.java`, so you find it by opening one file instead of searching a directory.

</RulesBox>

### Constants

Use a `Constants` class so no CAN ID or setpoint is ever typed twice. Organize it with one nested class per subsystem.

```java
package frc.robot;

public final class Constants {
    // Runtime mode — see Simulation Basics
    public static final Mode currentMode = RobotBase.isReal() ? Mode.REAL : simMode;
    public static final boolean tuningMode = true;

    public static class IntakeConstants {
        public static final int FRONT_INTAKE_RIGHT_MOTOR_PORT = 21;
        public static final int FRONT_INTAKE_LEFT_MOTOR_PORT = 22;
        public static final int INTAKE_PIVOT_MOTOR_PORT = 23;

        public static final double INTAKE_PIVOT_UP = 0.0;
        public static final double INTAKE_PIVOT_DOWN = 38.0;
        public static final double INTAKE_PIVOT_TOLERANCE = 0.5;

        public static final double INTAKE_PIVOT_KP = 4.8;
        public static final double INTAKE_PIVOT_KG = 0.35;
    }

    public static class ShooterConstants {
        public static final int RIGHT_SHOOTER_PORT = 31;
        public static final int LEFT_SHOOTER_PORT = 32;
    }

    public static class FieldConstants { /* field geometry, tag layout */ }
    public static class BLineConstants { /* follower PIDs, default path constraints */ }
}
```

Pull them into a subsystem with a **static import**, so each constant is used by its bare name:

```java
import static frc.robot.Constants.IntakeConstants.*;

public class Intake extends SubsystemBase {
    TalonFX pivot = new TalonFX(INTAKE_PIVOT_MOTOR_PORT);
```

Not `Constants.IntakeConstants.INTAKE_PIVOT_MOTOR_PORT` on every line. The static import is what makes the short form legal — and it is also why constant names should be long and specific. `INTAKE_PIVOT_MOTOR_PORT` is unambiguous once imported into a file; `PORT` would not be.

Two habits worth naming explicitly, because plenty of FRC code does the opposite:

**No `m_` prefix on fields you write.** WPILib's own examples use `m_motor`; this curriculum uses `motor` on student-owned classes. Editors already colour fields differently from locals, so the prefix adds characters to every reference without adding information.

Generated Tuner X files keep CTRE's `m_` names. Leave those as generated.

**No `k` prefix on constants you write.** `INTAKE_PIVOT_DOWN`, not `kIntakePivotDown`. `TunerConstants` keeps the generator's `k` names — do not rename them by hand.

Whichever conventions you adopt, hold to them across the whole project. Two styles in one repository is worse than either style alone.

### Subsystem Files

Each subsystem holds hardware objects and the methods that drive them.

```java
package frc.robot.subsystems.conveyor;

import static frc.robot.Constants.ConveyorConstants.*;

public class Conveyor extends SubsystemBase {
  TalonFX conveyor = new TalonFX(CONVEYOR_MOTOR_PORT);
  TalonFXConfiguration config = new TalonFXConfiguration();

  public Conveyor() {
    config.MotorOutput.NeutralMode = NeutralModeValue.Coast;
    config.CurrentLimits.StatorCurrentLimitEnable = true;
    config.CurrentLimits.SupplyCurrentLimitEnable = true;
    config.CurrentLimits.StatorCurrentLimit = 60;
    config.CurrentLimits.SupplyCurrentLimit = 40;

    PhoenixUtil.tryUntilOk(5, () -> conveyor.getConfigurator().apply(config));
  }

  @AutoLogOutput(key = "Conveyor/velocity")
  public double getConveyorVelocity() {
    return conveyor.getVelocity().getValueAsDouble();
  }

  @AutoLogOutput(key = "Conveyor/dutyCycle")
  public double setConveyorDutyCycle(double dc) {
    conveyor.set(dc);
    return dc;
  }

  public Command setConveyorCommand(double speed) {
    return run(() -> setConveyorDutyCycle(speed));
  }
}
```

<RulesBox title="Subsystem Guidelines" subtitle="Organization rules:">

- **One subsystem per package.** The package holds the subsystem plus any IO interfaces it needs.
- **All IDs and setpoints from `Constants`,** static-imported.
- **Configure in the constructor,** and retry the apply — see [Subsystems](/frc/subsystems).
- **Simple methods.** The subsystem knows *how*; commands decide *when*.
- **Command factories belong here.** A single-subsystem action is a method on the subsystem, not a class elsewhere.
- **Keep `periodic()` nearly empty.** Logging and safety checks only; behaviour lives in commands.

</RulesBox>

### Log Key Naming

Anything logged gets a key that reads like a path:

```java
@AutoLogOutput(key = "Intake/Position")
public double getIntakePosition() {
  return pivot.getPosition().getValueAsDouble();
}
```

Log viewers such as AdvantageScope build their tree from the slashes, so `Intake/Position` and `Intake/velocity` group together automatically. Start every key with the subsystem name and stay consistent — a key nobody can find during a match may as well not have been recorded.

### RobotContainer

`RobotContainer` centralizes setup and wiring. It holds initialization only, never runtime behaviour.

```java
public class RobotContainer {
    public final CommandSwerveDrivetrain drivetrain = TunerConstants.createDrivetrain();
    private final VisionFusion fusion = new VisionFusion(drivetrain, new VisionSubsystem());
    private final BLineAutos autos = new BLineAutos(drivetrain, fusion::resetPose);
    private final Telemetry logger = new Telemetry();
    Intake intake;
    Shooter shooter;

    private final CommandXboxController joystick = new CommandXboxController(0);
    private final SendableChooser<Command> autoChooser = new SendableChooser<>();

    public RobotContainer() {
        intake = new Intake();
        shooter = new Shooter();

        BLineAutos.registerLogging();
        drivetrain.registerTelemetry(logger::telemeterize);
        configureDefaultDrive();
        configureButtonBindings();
        configureAutos();
    }

    private void configureAutos() {
        autoChooser.setDefaultOption("Do nothing", Commands.none());
        autoChooser.addOption("Score left", autos.followFirstPath("score-left"));
        SmartDashboard.putData("Auto Chooser", autoChooser);
    }

    private void configureButtonBindings() {
        joystick.leftBumper().onTrue(drivetrain.runOnce(fusion::seedFieldCentric));

        AimAtGoalCommand aim = new AimAtGoalCommand(drivetrain, this::teleopFieldSpeeds);
        joystick.rightBumper().and(RobotModeTriggers.teleop()).whileTrue(aim);

        intake.setDefaultCommand(intake.intakeDefaultCommand());
        shooter.setDefaultCommand(shooter.setDutyCycleSetpointCommand(0));
        joystick.povDown().whileTrue(intake.intakeDeployCommand());
    }

    public Command getAutonomousCommand() {
        return autoChooser.getSelected();
    }
}
```

A fresh generated project does not need AdvantageKit. `LoggedDashboardChooser`, `AutoBuilder`, and `new Drive(...)` belong only to the optional IO-layer later track.

<RulesBox title="RobotContainer Guidelines" subtitle="Organization rules:">

- **Group by function:** separate methods for bindings, named commands, and auto setup.
- **No loop logic.** Configuration only — behaviour belongs in commands.
- **Every mechanism you write gets a default command,** or it never stops. The generated drivetrain uses `Idle` outside teleop so a finished auto cannot fall through to live sticks.
- **Bind factories directly.** `intake.deployAndIntakeCommand()` reads better than `new DeployAndIntakeCommand(intake)`.
- **Provide `getAutonomousCommand()`.**

</RulesBox>

### Utility Classes

Helpers belong in `util/`. A few earn their place on almost every robot:

```java
package frc.robot.util;

public class PhoenixUtil {
    /** Attempts to run the command until no error is produced. */
    public static void tryUntilOk(int maxAttempts, Supplier<StatusCode> command) {
        for (int i = 0; i < maxAttempts; i++) {
            var error = command.get();
            if (error.isOK()) break;
        }
    }
}
```

Others worth having: deadband and clamp helpers, and a tunable-constant wrapper (see [Tunable Constants and Characterization](/frc/tunable-constants)).

<RulesBox title="General Organization Rules" subtitle="Best practices:">

- **One class per file,** file name matching the class.
- **Clear separation:** subsystems own hardware; commands own decisions.
- **Dependency injection.** Pass subsystems into multi-subsystem commands via the constructor; no static subsystem instances.
- **Nested constant classes,** static-imported at the point of use.
- **Consistent naming** across the whole repository.
- **Descriptive names.** `INTAKE_PIVOT_DOWN` beats `POS_2`.

</RulesBox>
