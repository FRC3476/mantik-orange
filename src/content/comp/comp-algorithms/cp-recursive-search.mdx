### Why recursion

Nested loops work when you know how many choices there are while writing the code. Three nested loops pick three things. But if the problem picks `K` things and `K` comes from the input, you cannot write `K` nested loops.

Recursion handles this: one function call per level of choice, with the depth determined at runtime.

### The pattern

Every recursive search has the same three parts.

<StepsBox title="Structure">

1. **Base case.** All decisions made — evaluate the completed candidate and return.
2. **Loop over choices** available at this position.
3. **Choose, recurse, undo.** Apply a choice, recurse to the next position, then reverse the choice before trying the next one.

</StepsBox>

The undo step is what makes the search correct. Without it, choices leak from one branch into the next.

### Generating subsets

*Print every subset of N items.*

```java
static int n;
static int[] a;
static List<Integer> current = new ArrayList<>();

static void search(int i) {
    if (i == n) {                     // base case: decided about every item
        System.out.println(current);
        return;
    }

    // choice 1: skip item i
    search(i + 1);

    // choice 2: take item i
    current.add(a[i]);
    search(i + 1);
    current.remove(current.size() - 1);   // undo
}
```

Two choices at each of N positions gives 2<sup>N</sup> leaves, matching the bitmask approach from [Complete Search](/comp/cp-complete-search). The recursive version is more flexible: pruning is natural, and the choice set at each step can depend on earlier choices.

<RulesBox title="Reading the undo line">

`current.remove(current.size() - 1)` removes the last element — the one just added. Every `add` before a recursive call needs a matching `remove` after it.

If you forget it, `current` keeps growing and every subsequent branch sees contaminated state. The symptom is output that is correct for the first branch and wrong afterward.

</RulesBox>

### Generating permutations

*Print every ordering of N items.*

```java
static boolean[] used;

static void permute(int depth) {
    if (depth == n) {
        System.out.println(current);
        return;
    }

    for (int i = 0; i < n; i++) {
        if (used[i]) continue;

        used[i] = true;
        current.add(a[i]);

        permute(depth + 1);

        current.remove(current.size() - 1);
        used[i] = false;                    // undo both
    }
}
```

Here `used` tracks which items are already placed, so each appears exactly once per ordering. Both pieces of state — the list and the `used` flags — must be undone.

N! grows fast: 10! is about 3.6 million, which is fine, and 12! is 479 million, which is not. Check N against the table before choosing this approach.

### Choosing K of N

*Print every combination of exactly K items, in increasing index order.*

```java
static void choose(int start, int k) {
    if (current.size() == k) {
        System.out.println(current);
        return;
    }

    // not enough items left to reach size k — prune
    if (n - start < k - current.size()) return;

    for (int i = start; i < n; i++) {
        current.add(a[i]);
        choose(i + 1, k);
        current.remove(current.size() - 1);
    }
}
```

Passing `i + 1` as the next `start` keeps indices increasing, so each combination is produced once rather than in every order.

The prune is worth including. Once the remaining items cannot fill the quota, the whole branch is dead, and cutting it early avoids a large amount of pointless work.

### Grid search

Recursion over grid cells is the shape behind many counting problems.

*Count paths from the top-left to the bottom-right of an R × C grid, moving only right or down, avoiding blocked cells.*

```java
static int count(int r, int c) {
    if (r >= rows || c >= cols) return 0;      // off the grid
    if (grid[r][c] == '#') return 0;           // blocked
    if (r == rows - 1 && c == cols - 1) return 1;   // arrived

    return count(r + 1, c) + count(r, c + 1);
}
```

No undo is needed here because nothing mutable is being modified — each call returns a value rather than accumulating into shared state. That is often the simpler formulation when it applies.

This particular version recomputes the same cells repeatedly, so it is exponential. On a small grid that is acceptable. On a large one you would cache results per cell, which is dynamic programming — see Introduction to DP.

### Pruning

Cutting a branch as soon as it cannot lead to a valid answer is what makes recursive search practical on larger inputs.

```java
static void search(int i, long sum) {
    if (sum > target) return;          // already too big — abandon
    if (i == n) {
        if (sum == target) found = true;
        return;
    }
    search(i + 1, sum);
    search(i + 1, sum + w[i]);
}
```

Passing `sum` as a parameter instead of recomputing it at the base case is the other half of this. It makes the prune possible and removes the inner loop, so each node costs constant time.

<RulesBox title="Pruning checklist">

- Prune when the partial state already violates a constraint.
- Prune when the best possible completion still cannot beat the current best answer.
- Order choices so the promising ones come first — this makes bound-based pruning cut more.
- Only add a prune whose condition is genuinely reachable. A test that never fires is pure overhead.

</RulesBox>

### Recursion depth

Java's default stack handles depth in the low tens of thousands. A search whose depth is N with N ≤ 20 is nowhere near that. But a recursion whose depth scales with a large input — a DFS over 200,000 nodes — can overflow. See the thread-with-larger-stack workaround in [Debugging Under Time Pressure](/comp/cp-debugging).

<RulesBox title="Common mistakes">

- **Missing undo.** State leaks between branches. Every mutation before a recursive call needs its reverse after.
- **Sharing a mutable object incorrectly.** If you store `current` itself into a results list, every entry aliases the same list. Store a copy: `new ArrayList<>(current)`.
- **Wrong base case.** `i == n` versus `i == n - 1` — the first means all items decided, the second means all but one.
- **Passing `start` as `i` instead of `i + 1`** when generating combinations, which produces duplicates.
- **Unbounded growth.** Confirm every path reaches a base case.

</RulesBox>

<ExerciseBox title="Practice" description="Write each with the choose-recurse-undo pattern.">

1. Print all subsets of `{1, 2, ..., n}` whose sum is exactly `T`.
2. Print all permutations of a string's characters, without duplicates when characters repeat.
3. Given N ≤ 16 tasks and 2 workers, assign each task to a worker so the larger workload is as small as possible.
4. Count the ways to place K non-attacking rooks on an N × N board, for N ≤ 8.
5. Given a list of coin values and a target, count the distinct multisets of coins summing to the target.

<details>
<summary>Hints</summary>

1. Subset recursion, passing the running sum, pruning when it exceeds `T`.
2. Sort the characters first, then at each level skip a character equal to the previous one that has not been used — this suppresses duplicate orderings.
3. Two choices per task. Track both workers' totals; prune when one already exceeds the best answer so far.
4. One rook per row. Track which columns are taken with a `boolean[]`, exactly like the permutation example.
5. To avoid counting the same multiset in different orders, pass a `start` index and never go back to an earlier coin. Reusing the same coin means recursing with `start` unchanged rather than `start + 1`.

</details>

</ExerciseBox>
