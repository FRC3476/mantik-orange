### Hardware Manager

For a walkthrough of the Limelight Hardware Manager and a simple auto-align, see [Limelight and Auto Align Explanation](https://www.youtube.com/watch?v=p0Ux8Mk1ycQ).

Open the **Limelight Hardware Manager**. Find your camera and open its feed. Set the pipeline type to **AprilTags** and enable **Full 3D Targeting** for field pose.

This course's Java uses LimelightHelpers **v1.14**, which requires Limelight OS **2026.0** or later. Put the helper at `src/main/java/frc/robot/LimelightHelpers.java`. Download it from [Limelight Lib](https://docs.limelightvision.io/docs/docs-limelight/apis/limelight-lib).

### 2D targeting variables

These NetworkTables values describe where a target sits in the image. They are not the robot's field X/Y.

| Variable | Meaning |
| --- | --- |
| tx | Horizontal offset from the crosshair to the target, in degrees |
| ty | Vertical offset from the crosshair to the target, in degrees |
| ta | Target area as a percent of the image (0–100). Larger usually means closer. |
| tl | Pipeline (processing) latency, milliseconds |
| cl | Capture latency, milliseconds |

Check the sign of `tx`/`ty` in the Limelight UI and the [NetworkTables API](https://docs.limelightvision.io/docs/docs-limelight/apis/complete-networktables-api) for your OS version. Do not treat them as WPILib field axes.

`tl` and `cl` are separate. There is no single fixed latency such as 6 ms. LimelightHelpers pose timestamps are already latency-adjusted. Do not subtract `tl` or `cl` again in robot code.

### 3D localization (MegaTag)

`Robot Pose in Target Space` is the robot relative to the tag. `Robot Pose in Field Space` is the robot on the field. Fusion in this course uses the WPILib blue-origin field pose (`botpose_wpiblue` / `getBotPoseEstimate_wpiBlue`), for both alliances.

This path teaches MegaTag1. MegaTag2 can be more stable when the gyro heading you send it is correct. It is optional further reading; it requires `SetRobotOrientation` every loop.

### Camera mount

Measure the camera relative to the robot origin (drivebase center, at the floor): forward/back, left/right, up, and roll/pitch/yaw.

Keep the UI mount and any `setCameraPose_RobotSpace` call identical. If the UI already holds the measured mount, do not overwrite it from code with placeholder numbers. If code is the source of truth, write the measured meters and degrees there.

Example numbers (replace with your measurements): 0.32 m forward, 0.27 m up, −15° pitch.

### Fusion, not a reset

Odometry drift is real. Vision should be a **weighted correction** into `CommandSwerveDrivetrain.addVisionMeasurement`, not a hard `resetPose` on every tag. The next two lessons show that insertion path.
