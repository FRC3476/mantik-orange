### Introduction to Odometry

Odometry estimates pose from wheel encoders and a gyroscope. It starts from a known pose and integrates motion — dead reckoning. It does not need cameras or field tags.

Updates are continuous and fast. Error still accumulates from slip, compression, and sensor noise. Vision later pulls that estimate back toward the field. Odometry is the baseline that runs whether tags are visible or not.

This course's swerve drivetrain is Tuner X `CommandSwerveDrivetrain`. Phoenix already runs a high-rate odometry thread. You read `getState().Pose` (or `getStateCopy().Pose` when you keep a snapshot). You do not construct `SwerveDriveKinematics`, `SwerveDriveOdometry`, or `SwerveDrivePoseEstimator` as the robot drivetrain.

Learn more: [WPILib: Odometry](https://docs.wpilib.org/en/stable/docs/software/kinematics-and-odometry/index.html) · [Using the Swerve Drivetrain](https://v6.docs.ctr-electronics.com/en/latest/docs/api-reference/mechanisms/swerve/using-swerve-api.html)

### Odometry principles

**Dead reckoning.** From a known pose, each movement changes X, Y, and heading. Those changes accumulate.

**Wheel distance.** Encoders measure shaft rotation. Combined with wheel diameter — and gear ratio, if the encoder is on the motor shaft — that becomes distance.

**Heading.** A gyro (Pigeon 2 on the course swerve) provides heading. Wheel-only heading during turns is worse.

**Drift.** Slip, tread wear, and a wrong wheel radius all integrate into pose error. Characterization and vision fusion exist because of that, not instead of odometry.

### Sensors

**Drive encoders** on each module's drive motor (Talon FX integrated encoder in the course stack).

**Steer encoders** (CANcoder, or PWM into CANdi / Talon FXS) so each module's wheel direction is known.

**Gyro.** Pigeon 2.0 is required by the Phoenix swerve API.

Tuner X measures offsets and writes them into `TunerConstants.java`. Do not invent those numbers in this lesson.

### Differential drive (conceptual)

A tank-style chassis uses left and right wheel distance plus a gyro. WPILib's `DifferentialDriveOdometry` is the matching class if you are not on swerve. This curriculum's examples from here on assume holonomic `CommandSwerveDrivetrain`.

Left vs right distance still explains the idea: average distance is forward motion, difference is rotation, gyro heading is more trustworthy than wheel-only yaw.

### CommandSwerveDrivetrain odometry

Phoenix samples module positions synchronously with the motor controllers on a separate thread (250 Hz on CANivore, 100 Hz on roboRIO CAN). Control runs inline with those updates. That is why the course does not start a second `PhoenixOdometryThread` or call `SwerveDriveOdometry.update` from the 20 ms loop.

```java
var state = drivetrain.getStateCopy();
Pose2d pose = state.Pose;
ChassisSpeeds speeds = state.Speeds; // robot-relative m/s and rad/s
boolean odometryValid = drivetrain.isOdometryValid();
```

`getState()` is the live object. Do not mutate it. Use `getStateCopy()` when you keep the snapshot or share it across threads.

`isOdometryValid()` is the readiness gate for vision inserts. A nonzero pose is not proof that history exists.

With `VisionFusion` installed, route `resetPose`, `resetRotation`, and `seedFieldCentric` through that class so accepted-history and trust are invalidated together.

Module order, kinematics, and desaturation stay inside Phoenix. Tuner X already captured module positions in `TunerConstants`.

### Simulation

Generated `CommandSwerveDrivetrain` starts a notifier that calls `updateSimState` with measured dt and battery voltage. Do not also call `updateSimState` from `simulationPeriodic()`. Desktop sim checks that control integrates. It does not prove traction, real calibration, or vision accuracy.

### Common mistakes

<RulesBox title="Odometry mistakes">

- Constructing a second WPILib estimator beside Phoenix.
- Reading `getState()` and mutating the returned object.
- Treating a nonzero pose as `isOdometryValid()`.
- Calling `seedFieldCentric` when the robot is not at the intended heading.
- Using `resetPose` on every AprilTag instead of `addVisionMeasurement`.
- Hand-editing wheel radius or offsets in `TunerConstants` instead of regenerating.

</RulesBox>
