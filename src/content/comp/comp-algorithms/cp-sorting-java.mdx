### Why sorting shows up everywhere

Sorting is rarely the answer by itself. It is the step that makes the actual answer obvious. Once values are in order, the largest is at the end, duplicates are adjacent, the median is in the middle, and "the closest pair of values" only needs to compare neighbors.

Recognizing that a problem gets easier in sorted order is the skill. The sorting itself is one library call.

### Sorting primitives

```java
int[] a = new int[n];
// ... read values ...
Arrays.sort(a);          // ascending, in place, O(N log N)
```

That is the whole thing for ascending order. Java has no descending sort for primitive arrays, which trips people up. Three options:

```java
// Option 1: sort ascending, then read backwards
Arrays.sort(a);
for (int i = n - 1; i >= 0; i--) { /* ... */ }

// Option 2: sort ascending, then reverse in place
Arrays.sort(a);
for (int i = 0, j = n - 1; i < j; i++, j--) {
    int t = a[i]; a[i] = a[j]; a[j] = t;
}

// Option 3: box it and use a comparator
Integer[] b = new Integer[n];
for (int i = 0; i < n; i++) b[i] = a[i];
Arrays.sort(b, Comparator.reverseOrder());
```

Option 1 is almost always the right choice. Option 3 works but boxes every value, which costs memory and time for no benefit.

<RulesBox title="Sorting part of an array">

`Arrays.sort(a, from, to)` sorts the range `[from, to)` — inclusive start, exclusive end. This matters when you used the "extra slot" trick for 1-based indexing:

```java
int[] a = new int[n + 1];
for (int i = 1; i <= n; i++) a[i] = nextInt();

Arrays.sort(a, 1, n + 1);     // NOT Arrays.sort(a)
```

Calling plain `Arrays.sort(a)` here sorts the unused zero at index 0 into position, shifting everything and producing a wrong answer.

</RulesBox>

### Sorting objects

When each input record has several fields, keep them together in a small class rather than in parallel arrays.

```java
static class Cow {
    int id, weight, age;
    Cow(int id, int weight, int age) {
        this.id = id;
        this.weight = weight;
        this.age = age;
    }
}
```

Then sort with a comparator that names the field:

```java
Cow[] cows = new Cow[n];
// ... fill ...

Arrays.sort(cows, Comparator.comparingInt(c -> c.weight));
```

Descending is the same call with `.reversed()`:

```java
Arrays.sort(cows, Comparator.comparingInt((Cow c) -> c.weight).reversed());
```

The explicit `(Cow c)` type is required once you chain `.reversed()`, because Java can no longer infer the lambda's parameter type. Omitting it produces a confusing compile error.

### Tie-breaking

Problems often specify a secondary ordering: "sort by weight; if equal, by age". Chain comparators with `thenComparing`.

```java
Arrays.sort(cows,
    Comparator.comparingInt((Cow c) -> c.weight)
              .thenComparingInt(c -> c.age));
```

Mixed directions work the same way — reverse only the part that needs it:

```java
// heaviest first; among equal weights, youngest first
Arrays.sort(cows,
    Comparator.comparingInt((Cow c) -> c.weight).reversed()
              .thenComparingInt(c -> c.age));
```

<RulesBox title="Writing a comparator by hand">

The lambda form returns a negative number, zero, or a positive number:

```java
Arrays.sort(cows, (x, y) -> x.weight - y.weight);
```

This is compact and fine for small values, but **subtraction overflows**. If weights can be near the `int` limit, `x.weight - y.weight` can wrap to the wrong sign and the sort will be silently wrong — or throw `IllegalArgumentException: Comparison method violates its general contract`.

Use `Integer.compare` instead, which never overflows:

```java
Arrays.sort(cows, (x, y) -> Integer.compare(x.weight, y.weight));
```

Make this the default habit. The subtraction form saves nothing.

</RulesBox>

### Sorting with the original index

Sometimes you need to know where a value came from after sorting. Sort an array of index pairs rather than the values alone.

```java
Integer[] idx = new Integer[n];
for (int i = 0; i < n; i++) idx[i] = i;

Arrays.sort(idx, (x, y) -> Integer.compare(a[x], a[y]));

// idx[0] is the position of the smallest value in the original array
```

### Problems that sorting solves

The fourth row is worth internalizing. Checking every pair for the minimum difference is O(N<sup>2</sup>); after sorting, the closest pair must be adjacent, so one linear pass suffices:

```java
Arrays.sort(a);
int best = Integer.MAX_VALUE;
for (int i = 1; i < n; i++) {
    best = Math.min(best, a[i] - a[i - 1]);
}
```

### Counting sort

When values are integers in a small known range, you can sort in O(N + range) by counting occurrences.

```java
// values guaranteed between 0 and 1000
int[] count = new int[1001];
for (int i = 0; i < n; i++) count[a[i]]++;

int pos = 0;
for (int v = 0; v <= 1000; v++) {
    for (int c = 0; c < count[v]; c++) {
        a[pos++] = v;
    }
}
```

This is rarely necessary — `Arrays.sort` is fast enough — but the frequency array itself is broadly useful, and often you want the counts rather than the sorted list.

<RulesBox title="Common mistakes">

- **Sorting when order matters.** If the problem's answer depends on the input order, sorting destroys it. Sort a copy, or sort indices.
- **`Arrays.sort` on a padded array** without a range. See the 1-based indexing note above.
- **Subtraction in a comparator** with large values.
- **Expecting a descending overload** for primitives. It does not exist.
- **`Arrays.sort` on primitives has an adversarial worst case.** Its dual-pivot quicksort can be driven to O(N<sup>2</sup>). Rarely a practical concern; if you need a guarantee, sort boxed values, which uses a merge sort.

</RulesBox>

<ExerciseBox title="Practice" description="Each of these is short once you decide what to sort by.">

1. Read N integers and print them in descending order.
2. Read N cows, each with a name and a weight, and print the names ordered by weight descending, breaking ties alphabetically.
3. Read N integers and print the smallest absolute difference between any two of them.
4. Read N integers and print the number of distinct values, without using a set.
5. Read N intervals `[start, end]` and print the maximum number that overlap at any single point.

<details>
<summary>Hints</summary>

1. Sort ascending, print backwards.
2. `Comparator.comparingInt(...).reversed().thenComparing(c -> c.name)`.
3. Sort, then compare adjacent pairs only.
4. Sort, then count positions where the value differs from the previous one — plus one for the first element.
5. Not a simple sort of intervals. Make a list of events: `+1` at each start, `-1` at each end. Sort by coordinate, then sweep, keeping a running total and tracking its maximum. Decide carefully whether an interval ending exactly where another begins counts as overlapping — the statement will say.

</details>

</ExerciseBox>
