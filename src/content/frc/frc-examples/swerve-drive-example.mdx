### Overview

A swerve drivetrain is the largest subsystem on most robots and the one you are least likely to write from scratch. This course uses the Phoenix Tuner X Swerve Project Generator. It writes hardware constants and a command-based drivetrain that already owns motors, odometry, simulation, and SysId hooks.

Do not roll your own `SwerveDriveKinematics`, `SwerveDriveOdometry`, or `SwerveDrivePoseEstimator` as the robot drivetrain. Phoenix already owns those.

API versions for the Java below: **WPILib 2026.2.2**, **Phoenix 6 26.3.0**, **BLine-Lib v0.9.1**.

### TunerConstants Comes From Tuner X

`TunerConstants.java` is produced by the **Phoenix Tuner X Swerve Project Generator**. You do not edit it by hand and you do not derive its numbers yourself — the generator walks you through the hardware and writes the file.

```java
// Generated by the 2026 Tuner X Swerve Project Generator
// https://v6.docs.ctr-electronics.com/en/stable/docs/tuner/tuner-swerve/index.html
public class TunerConstants {
    private static final Slot0Configs steerGains = new Slot0Configs()
        .withKP(100).withKI(0).withKD(0.5)
        .withKS(0.1).withKV(1.91).withKA(0)
        .withStaticFeedforwardSign(StaticFeedforwardSignValue.UseClosedLoopSign);

    private static final Slot0Configs driveGains = new Slot0Configs()
        .withKP(0.1).withKI(0).withKD(0)
        .withKS(0).withKV(0.124);

    public static final LinearVelocity kSpeedAt12Volts = MetersPerSecond.of(4.54);

    public static CommandSwerveDrivetrain createDrivetrain() {
        return new CommandSwerveDrivetrain(
            DrivetrainConstants, FrontLeft, FrontRight, BackLeft, BackRight);
    }
}
```

The nested `TunerSwerveDrivetrain` class is also generated. `CommandSwerveDrivetrain` extends it. When you re-run the generator, it overwrites `TunerConstants.java`. Keep `CommandSwerveDrivetrain`, `BLineAutos`, `VisionFusion`, and `Telemetry` in files the generator does not own.

<StepsBox title="Generating swerve constants">

1. Open **Phoenix Tuner X** and connect to the robot.
2. Run the **Swerve Project Generator**. Confirm firmware, device types, CAN bus, and IDs match [swerve requirements](https://v6.docs.ctr-electronics.com/en/latest/docs/tuner/tuner-swerve/swerve-system-requirements.html).
3. Enter the drivetrain layout: motor and encoder IDs, gear ratios, wheel radius, module positions.
4. Let it run the self-test routines — they measure the CANcoder offsets for you.
5. It writes `TunerConstants.java`. Place it in `frc/robot/generated/`.
6. Re-tune `driveGains` and `steerGains` afterwards in the generator, then regenerate. Velocity-controlled autos need those gains and feedforward before they are useful.

</StepsBox>

<RulesBox title="Do not hand-edit generated files">

The header says "Generated by". The next person to run the generator will overwrite anything you changed, and the two versions will disagree in ways that are hard to spot.

If a value needs to change, change it in the generator's input and regenerate. If it does not belong to the generator at all, put it in `Constants.java` or a helper class instead.

</RulesBox>

### CommandSwerveDrivetrain

Tuner X also writes `CommandSwerveDrivetrain`. It implements WPILib `Subsystem`, constructs hardware from `TunerConstants`, and already:

- applies operator perspective in `periodic()` (blue 0°, red 180°)
- runs `updateSimState` on a 4 ms notifier in simulation — do **not** also call it from `simulationPeriodic()`
- converts FPGA capture timestamps in `addVisionMeasurement` / `samplePoseAt` via `Utils.fpgaToCurrentTime`
- exposes `applyRequest`, SysId, and `registerTelemetry`

Add course helpers around that class. Do not replace its constructors, perspective update, simulation notifier, or timestamp overrides with an incomplete skeleton.

```java
public Command applyRequest(Supplier<SwerveRequest> request) {
    return run(() -> this.setControl(request.get()));
}
```

`applyRequest` is a **command factory**. Use it to build default teleop and simple button bindings. Do not call it from inside another command's `execute`. Nested control uses `setControl(request)`.

Read pose and chassis speeds from a copy when you keep the snapshot:

```java
var state = drivetrain.getStateCopy();
Pose2d pose = state.Pose;
ChassisSpeeds speeds = state.Speeds; // robot-relative m/s and rad/s
```

`getState()` is the live object. Do not mutate it. `Speeds` are robot-relative.

Heading seed (`seedFieldCentric`) changes the **pose heading**, not only a joystick offset. Use it when the robot orientation is known. Path and vision pose initialization use `resetPose` / `resetRotation`. With vision installed, route those through `VisionFusion` so accepted-history is invalidated too. Routine vision updates use `addVisionMeasurement`, not resets.

### Default drive

Construction is one line:

```java
public final CommandSwerveDrivetrain drivetrain = TunerConstants.createDrivetrain();
```

Teleop field-centric drive uses `SwerveRequest.FieldCentric` with joystick negations, a 10% translation/rotation deadband, and `DriveRequestType.OpenLoopVoltage`. Max translation comes from `TunerConstants.kSpeedAt12Volts` in m/s. Scale and deadband the sticks **once**.

Gate joystick output to teleop. Outside teleop the default request is `Idle`, so an empty or completed auto cannot fall through to live sticks. Keep the generated disabled Idle binding with `.ignoringDisable(true)`.

```java norun
private final double MaxSpeed = TunerConstants.kSpeedAt12Volts.in(MetersPerSecond);
private final double MaxAngularRate = RotationsPerSecond.of(0.75).in(RadiansPerSecond);

private final SwerveRequest.FieldCentric m_drive = new SwerveRequest.FieldCentric()
        .withDeadband(MaxSpeed * 0.1)
        .withRotationalDeadband(MaxAngularRate * 0.1)
        .withDriveRequestType(DriveRequestType.OpenLoopVoltage);
private final SwerveRequest.Idle m_idle = new SwerveRequest.Idle();

drivetrain.setDefaultCommand(
        Commands.either(
                drivetrain.applyRequest(() ->
                        m_drive.withVelocityX(-m_joystick.getLeftY() * MaxSpeed)
                                .withVelocityY(-m_joystick.getLeftX() * MaxSpeed)
                                .withRotationalRate(-m_joystick.getRightX() * MaxAngularRate)),
                drivetrain.applyRequest(() -> m_idle),
                DriverStation::isTeleopEnabled));

RobotModeTriggers.disabled().whileTrue(
        drivetrain.applyRequest(() -> m_idle).ignoringDisable(true));
```

X is forward and Y is left in the WPILib convention. Joysticks report forward as negative, which is why the Y axes are negated.

A default command may start after another command ends. It is not a substitute for writing zero/idle in the ending command's `end()`.

### Robot lifecycle

`Robot.java` runs the scheduler. It does not call subsystem `periodic()` by hand and it does not create a second scheduler.

```java norun
@Override
public void robotPeriodic() {
    CommandScheduler.getInstance().run();
}

@Override
public void autonomousInit() {
    m_autonomousCommand = m_robotContainer.getAutonomousCommand();
    if (m_autonomousCommand != null) {
        CommandScheduler.getInstance().schedule(m_autonomousCommand);
    }
}

@Override
public void teleopInit() {
    if (m_autonomousCommand != null) {
        m_autonomousCommand.cancel();
        m_autonomousCommand = null;
    }
}
```

Cancel the auto on `disabledInit` as well so a disable mid-path cannot resume into teleop sticks.

### Path following

BLine stays the course auto tool. Keep one configured `FollowPath.Builder` in `BLineAutos`, **not** inside generated Tuner files. The builder's subsystem argument is the drivetrain. Pose and speeds come from `getStateCopy()`. The consumer calls `setControl` because `FollowPath` is already the running command.

```java norun
m_applyRobotSpeeds = new SwerveRequest.ApplyRobotSpeeds()
        .withDriveRequestType(DriveRequestType.Velocity)
        .withDesaturateWheelSpeeds(true);

m_builder = new FollowPath.Builder(
        drivetrain,
        () -> drivetrain.getStateCopy().Pose,
        () -> drivetrain.getStateCopy().Speeds,
        this::applyRobotRelative,
        new PIDController(5.0, 0.0, 0.0),
        new PIDController(3.0, 0.0, 0.0),
        new PIDController(2.0, 0.0, 0.0))
        .withTRatioBasedTranslationHandoffs(true)
        .withDefaultShouldFlip();
```

`ApplyRobotSpeeds` defaults to open-loop voltage. Set `DriveRequestType.Velocity` explicitly. That request needs tuned drive kS/kV/kP in `TunerConstants`.

BLine v0.9.1 converts field output to robot-relative speeds and does **not** discretize. `ApplyRobotSpeeds` does not discretize either. Call `ChassisSpeeds.discretize(speeds, 0.020)` **once** in the adapter. That 20 ms is the follower period, not Phoenix's odometry or sim thread. Do not discretize again in aim or teleop, and do not add Choreo wheel-force arrays that BLine does not provide.

Phoenix still owns module kinematics, optimization, and wheel-speed desaturation.

Inject `drivetrain::resetPose` when vision is absent, and `fusion::resetPose` when `VisionFusion` exists. First path only: `withPoseReset`. Later paths: `withPoseReset(pose -> {})`. A separate runtime-target builder has no flip and no reset.

Zero output on completion and interruption (`finallyDo`). Add a timeout around a blocked route when you need one. Mechanism events must not require the drivetrain.

Full adapter, logging, and flip rules: [BLine](/frc/bline). CTRE's [SwerveWithChoreo](https://github.com/CrossTheRoadElec/Phoenix6-Examples/tree/main/java/SwerveWithChoreo) example uses the same drivetrain class with Choreo instead of BLine. This course does not.

### Auto chooser

```java
m_autoChooser.setDefaultOption("Do nothing", Commands.none());
m_autoChooser.addOption("Score left", m_autos.followFirstPath("score-left"));
SmartDashboard.putData("Auto Chooser", m_autoChooser);
```

Log the selected option when `getAutonomousCommand()` runs. `SendableChooser` is enough; logging a choice is not exclusive to AdvantageKit.

<RulesBox title="Common mistakes">

- **Editing `TunerConstants.java` by hand.** Regenerate instead.
- **Calling `applyRequest` from `execute`.** Use `setControl` inside an already-running command.
- **Joystick default command outside teleop**, so a finished auto drives from live sticks.
- **Aim and heading seed on the same bumper.**
- **Feeding field-relative or driver-perspective speeds** into `FollowPath`. The consumer must be robot-relative.
- **Resetting pose on every path**, or resetting from the authored blue start after the builder already flipped for red.
- **Skipping `discretize` in the BLine adapter**, or discretizing twice.
- **Open-loop `ApplyRobotSpeeds` in auto** after you intended Velocity control.
- **Forgetting joystick negations,** giving a robot that drives backwards.

</RulesBox>
